# 03 — Phase 2 开发实施指南

本文档是 Phase 2 的 **主实施手册**：按推荐顺序分步推进，每步含目标、涉及文件、完成标志。  
**只写设计与流程，不包含具体代码实现。**

---

## 总览：推荐实施顺序

```
Step 0  对齐接口（与 Phase 3）+ 建分支
   ↓
Step 1  数据库：knowledge_documents + ORM
   ↓
Step 2  RAG 层：TenantFilter 与 retrieve 签名
   ↓
Step 3  知识库 API：上传 / 列表 / 删除 / 搜索
   ↓
Step 4  MemoryManager + 长/情景记忆 user_id
   ↓
Step 5  skill 连接级上下文
   ↓
Step 6  file_reader 用户目录隔离
   ↓
Step 7  前端 KnowledgeView + 联调
   ↓
Step 8  验收与文档收尾
```

各 Step 可拆 PR；**Step 1～3 建议同一 PR 或连续合并**，避免中间状态「有表无 filter」。

## Step 2 — RAG 层 Tenant Filter 框架

### 目标
在向量路与图谱路统一注入租户 filter；**预留 `user_type` 扩展点**。

### 2.1 核心接口（必须与 Phase 3 一致）

建议在 `app/rag/tenant_filter.py`（新模块）集中定义：

```
build_private_filter(user_id: int) -> dict
  → Phase 2 唯一实现

build_retrieval_filter(user_id: int, user_type: str = "regular") -> dict
  → Phase 2：等价于 build_private_filter
  → Phase 3：member 用户增加 OR visibility=member
```

**HybridRetriever.retrieve** 扩展签名：

```
retrieve(
  query: str,
  top_k: int = 5,
  mode: Literal["vector", "graph", "hybrid"] = "hybrid",
  *,
  user_id: int | None = None,      # Phase 2 必填（生产路径）
  user_type: str = "regular",      # Phase 2 传入但不改变 filter
  rrf_k: int | None = None,
) -> list[Document]
```

**规则**：
- `user_id is None`：仅允许 `AUTH_ENABLED=false` 匿名开发路径；生产 API 必须传
- Phase 2 内 `_hybrid_retrieve` / vector / graph 三路均应用同一 filter

### 2.2 涉及文件

| 文件 | 改动 |
|------|------|
| `app/rag/tenant_filter.py` | **新建** filter 构建 |
| `app/rag/hybrid.py` | retrieve / add_knowledge / delete / list 签名扩展 |
| `app/rag/vector_store.py` | query/get_all 支持 where metadata filter |
| `app/rag/knowledge_graph.py` | Cypher 加 user_id 条件 |
| `app/db/chroma.py` | 封装 `where` 参数传递（若尚未支持） |
| `app/db/neo4j.py` | Document/Entity 写入带 user_id；查询带 filter |

### 2.3 Chroma metadata 规范（Phase 2 起强制）

每条 knowledge 文档 metadata 至少含：

```json
{
  "doc_id": "uuid",
  "user_id": 123,
  "visibility": "private",
  "source": "knowledge_upload"
}
```

长期记忆 collection（`long_term_memory`）同理增加 `user_id`（Step 4）。

### 2.4 Neo4j 节点规范

- `Document` 节点：`doc_id`, `user_id`, `visibility`
- `Entity` 节点：建议复合键 `(user_id, name)` 或属性 `user_id` + 唯一约束策略（与现有 `name` 索引协调，避免跨用户实体串线）
- 会话相关 `Conversation` 节点：增加 `user_id`（情景记忆 Step 4）

### 2.5 add_knowledge 改造

```
add_knowledge(content, doc_id, user_id, metadata?, entities?, visibility="private")
```

写入 Chroma/Neo4j 时写入 metadata；**MySQL 行由 API 层或 service 层创建**（推荐新建 `knowledge_service.py`）。

### 2.6 完成标志
- [ ] 单元或脚本：用户 1 写入 doc，用户 2 retrieve 返回空
- [ ] `build_retrieval_filter` 文档注释标明 Phase 3 扩展点
- [ ] 现有匿名/local dev 路径不崩溃（`user_id=0` 策略写进 README 或 env 说明）

## Step 3 — 知识库 API 改造

### 目标
REST 层鉴权 + 归属 + 与 MySQL 元数据一致。

### 3.1 端点行为矩阵

| 端点 | 鉴权 | Phase 2 行为 |
|------|------|--------------|
| POST `/api/knowledge/upload` | 必须登录 | 写 private，`user_id=ctx.user_id` |
| POST `/api/knowledge/upload/file` | 必须登录 | 同上；文件存 `uploads/{user_id}/` |
| GET `/api/knowledge/documents` | 必须登录 | 仅 `user_id=self, visibility=private, deleted_at IS NULL` |
| DELETE `/api/knowledge/{doc_id}` | 必须登录 | MySQL 查 owner → 软删 + 删 Chroma/Neo4j |
| POST `/api/knowledge/search` | 必须登录 | retrieve 带 user_id |
| GET `/api/knowledge/stats` | 必须登录 | 仅统计当前用户 private 文档数 |

### 3.2 涉及文件
- `app/api/knowledge.py`（主改）
- `app/services/knowledge_service.py`（**建议新建**：协调 MySQL + RAG）
- `app/models/settings.py`（KnowledgeUpload 等，按需扩展）

### 3.3 删除流程（建议）

```
1. SELECT knowledge_documents WHERE id=doc_id AND user_id=ctx.user_id AND deleted_at IS NULL
2. 若无 → 404 或 403
3. 软删 MySQL
4. hybrid.delete_knowledge(doc_id, user_id=...)  // 向量/图谱按 user filter 删
5. audit log
```

### 3.4 Phase 3 预留
- 上传入口 **不要** 写死配额；在 service 层留 `# TODO(phase3): check_quota('document', ...)` 注释位
- 列表响应 JSON 增加字段 `visibility`，便于 Phase 3 追加 member 分区

### 3.5 完成标志
- [ ] 未登录调用 upload/list/search → 401
- [ ] A 上传后 B list 为空
- [ ] B 删 A 的 doc_id → 403/404
- [ ] MySQL 与 Chroma doc 数量一致（允许异步最终一致时写清策略）

## Step 5 — Skill 连接级激活（C-09）

### 目标
消除 `skill_registry` 全局单例导致的并发用户互相覆盖。

### 现状问题
`chat.py` 每条 WS 消息调用 `skill_registry.activate(skill_name)`，进程内全局，用户 A 激活 skill 会影响用户 B。

### 推荐方案（择一，团队统一）

**方案 A — 连接上下文（推荐）**
- WS accept 后创建 `ConnectionContext(active_skill=None)`
- 每条消息只更新本连接 context
- orchestrator / MemoryManager 从 context 读 active skill，**不**写全局 registry

**方案 B — registry 按 user_id+session_id 分槽**
- `activate(skill, scope=f"{user_id}:{session_id}")`
- 改动面较大，不推荐除非已有 scope 设计

### 涉及文件
- `app/api/chat.py`
- `app/skills/registry.py`（或新建 `connection_context.py`）
- `app/memory/manager.py` — `_resolve_context_strategy` 从 context 取 skill
- `app/agent/orchestrator.py` — 若读取 active skill

### 完成标志
- [ ] 两用户同时 WS：A 激活 skill X，B 不受影响
- [ ] 断开连接后 context 释放

## Step 6 — file_reader 用户目录（K-07）

### 目标
工具只能读当前用户 upload 目录，禁止路径穿越读取他人或系统文件。

### 规则
- 允许根：`./data/uploads/{user_id}/`
- 相对路径解析在该根下；禁止 `..`
- 绝对路径：仅当落在该用户根内
- Agent 调用 file_reader 时需注入 `user_id`（Tool 执行上下文扩展）

### 涉及文件
- `app/tools/builtin/file_reader.py`
- `app/tools/base.py` 或 executor — 传 user context
- `app/agent/` — 工具调用链传 user_id

### 上传与目录一致
Step 3 文件上传应保存至 `data/uploads/{user_id}/{filename}`，与 file_reader 对齐。

### 完成标志
- [ ] 用户 A 无法通过 file_reader 读 `uploads/{B}/` 下文件
- [ ] `../` 路径穿越被拒绝
