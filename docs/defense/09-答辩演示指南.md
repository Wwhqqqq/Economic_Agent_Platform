本文档提供完整的答辩/面试演示脚本、常见问题应答和注意事项。

## 1. 答辩前准备清单

### 1.1 环境启动

```bash
# 1. 配置 API Key
cp .env.example .env
# 编辑 .env，填入 DEEPSEEK_API_KEY

# 2. 启动基础设施（可选，记忆/RAG 需要）
docker-compose up -d

# 3. 启动后端
cd backend
pip install -r requirements.txt
uvicorn main:app --reload --host 0.0.0.0 --port 8000

# 4. 启动前端
cd frontend
npm install
npm run dev
```

或使用一键脚本：`start.bat`（Windows）/ `start.sh`（Linux）

### 1.2 验证

- [ ] `http://localhost:8000/health` 返回 `{"status": "healthy"}`
- [ ] `http://localhost:3000` 前端正常加载
- [ ] WebSocket 连接成功（Chat 页发送测试消息）
- [ ] `data/sample_financial.json` 内容已复制到剪贴板

### 1.3 备用方案

- 若 Docker 未启动：系统仍可运行，记忆/RAG 功能降级但不影响核心 demo
- 若 API Key 失效：提前准备截图/录屏作为 backup
- 若网络不稳定：提前录一段完整演示视频

## 3. 分场景演示脚本

### 场景 1：项目概览（2 分钟）

**操作：** 打开 Agents 页面

**话术：**
> 这是会计通用工作台，面向会计学场景。平台提供四种执行模式：智能路由、推理闭环、任务编排、协同决策。对应三种 Agent 引擎：ReAct 处理简单工具调用，Plan-Execute 处理多步骤审计任务，Multi-Agent 辩论处理需要多角度论证的财务评审。

---

### 场景 2：工具系统（2 分钟）

**操作：** 打开 Tools 页面

**话术：**
> 平台内置 10 个工具，分通用和会计两类。通用工具包括搜索、计算、文件读取；会计工具包括三大报表分析、财务比率、杜邦分析。这些工具是确定性 Python 实现，保证数字准确，LLM 只负责解读和组织报告。

---

### 场景 3：ReAct 工具调用（3 分钟）

**操作：** Chat 页，模式选 `reasoning_action`

**输入：**
```
请计算：如果一家公司净利润 350 万，股东权益 1000 万，总资产 2000 万，
分别计算 ROE 和 ROA，并评价其盈利能力。
```

**观察点：**
- thinking 事件
- calculator 或 financial_ratio_calculator 工具调用
- 最终 markdown 格式回答

**话术：**
> 这是 ReAct 模式——LLM 推理后决定调用工具，获取精确计算结果，再组织成人类可读的报告。

---

### 场景 4：财务审计 Pipeline（5 分钟）⭐ 重点

**操作：**
1. 激活 `financial_audit` 技能
2. Chat 页发送

**输入：**
```
请对以下公司进行完整财务审计：
[粘贴 sample_financial.json 全部内容]
```

**观察点：**
- 6 步工具按固定顺序调用（verify → analyze × 3 → ratio → dupont）
- 最终报告含 Executive Summary、Health Score、Risk Flags

**话术：**
> 财务审计技能使用了 Pipeline 模式——不是让 LLM 自己决定分析顺序，而是按照审计 SOP 固定执行：先验平衡、再三表分析、再算比率、最后杜邦分解。LLM 只负责最后一步，基于工具输出生成结构化审计报告。这保证了分析链条的完整性。

---

### 场景 5：Multi-Agent 辩论（5 分钟）⭐ 重点

**操作：** 模式选 `collaborative_decision`

**输入：**
```
请组织财务评审委员会，对示例科技股份有限公司进行多角度辩论分析。
重点关注：ROE水平、现金流质量、偿债风险。
[粘贴 sample_financial.json]
```

**观察点：**
- 三轮辩论，每轮 analyst → skeptic → judge
- Analyst 和 Skeptic 都调用了会计工具
- Skeptic 提出了 Analyst 未提及的风险
- 最终 Final Verdict 含结构化章节

**话术：**
> 这是项目的 Multi-Agent 协同决策引擎。分析师用工具做正面论证，质疑者专门找漏洞和风险，裁判每轮总结并推动讨论深入。相比单一 Agent，这种对抗式架构能覆盖更多分析盲区，更接近真实的财务评审流程。

---

### 场景 6：Plan-Execute 任务编排（3 分钟）

**操作：** 模式选 `task_orchestration`

**输入：**
```
请对示例科技股份有限公司进行全面的财务尽职调查，
包括三表分析、比率计算、杜邦分解，并给出投资建议。
[粘贴 JSON]
```

**观察点：**
- intermediate(phase=plan) 展示步骤列表
- 每步 execute_start → tool_call → execute_done
- evaluate 阶段
- 最终汇总报告

**话术：**
> Plan-Execute 适合复杂多步骤任务。LLM 先生成 JSON 执行计划，每步用 ReAct 执行，执行完评估是否需要重规划，最后汇总。这比纯 ReAct 更有结构，适合尽调报告这类长链路任务。

---

### 场景 7：知识库 RAG（3 分钟，可选）

**操作：**
1. Knowledge 页上传一份会计学文档
2. Chat 中提问文档相关内容

**话术：**
> 平台支持混合 RAG——向量检索捕捉语义相似，知识图谱捕捉实体关系，通过 RRF 算法融合。Agent 对话时自动检索相关知识注入上下文。

## 4. 常见问题应答库

### 架构类

**Q: 为什么不用 LangGraph？**
> 当前 ReAct 和 Plan-Execute 的手写循环已满足 demo 需求，逻辑透明便于调试和讲解。LangGraph 适合更复杂的状态图和条件分支，可作为后续演进。我们的重点是展示 Agent 范式本身，而非特定框架。

**Q: 为什么固定 DeepSeek？**
> Demo 阶段为了稳定性和成本控制，Agent 运行时固定 DeepSeek。LLMFactory 已支持多 Provider（OpenAI/Anthropic/Ollama），Settings 页面可配置，后续只需在 runtime 中读取前端传入的 provider 即可打通。

**Q: 三种 Agent 引擎如何选择？**
> 默认 adaptive 模式根据输入关键词自动路由。简单问答走 ReAct，含「审计、报告、尽调」走 Plan-Execute，含「辩论、评审」走 Multi-Agent。也可手动指定。

### 技术类

**Q: 工具调用怎么保证准确？**
> 会计工具是确定性 Python 计算，输入 JSON、输出精确数字。LLM 不直接做算术，只解读工具结果。Pydantic Schema 约束 LLM 的工具参数格式。

**Q: RRF 融合的原理？**
> Reciprocal Rank Fusion：对每个检索结果按排名算 1/(k+rank+1) 分，两路检索都排名靠前的文档融合分更高。k=60 是论文推荐默认值。优点是不需要分数归一化。

**Q: 记忆会撑爆上下文窗口吗？**
> 不会。每层记忆都有 top_k 限制和超时机制。短期记忆默认 10 条，RAG 召回 5 条，长期记忆也按相似度 top_k。加载失败时静默跳过。

**Q: Multi-Agent 辩论成本如何？**
> 3 轮 × 3 角色 = 9 次 LLM 调用 + 工具调用。Analyst 和 Skeptic 各最多 5 轮工具迭代。可通过 DEBATE_MAX_ROUNDS 配置轮次。

### 领域类

**Q: 能处理真实上市公司财报吗？**
> 当前接受 JSON 格式三表数据。扩展方向：Excel 解析器、XBRL 支持、对接 Wind/同花顺 API。

**Q: Health Score 怎么算的？**
> 目前由 LLM 基于工具输出综合判断（0-100）。可改为加权评分：各比率指标 × 权重 → 公式计算。

**Q: 审计报告合规吗？**
> 这是分析辅助工具，不是正式审计报告。输出仅供决策参考，不具备审计法律效力。

### 工程类

**Q: 怎么扩展新工具/技能？**
> 继承 BaseTool/BaseSkill，实现核心方法，在 main.py 注册，重启即可。详见文档 04 和 05。

**Q: 有测试吗？**
> 当前以手动 demo 验证为主。backend/test_ws_quick.py 有 WebSocket 快速测试。后续可补充 pytest 单元测试和集成测试。

**Q: 怎么部署生产？**
> 后端 Docker 化 + Nginx 反向代理 + 前端静态构建。ChromaDB/Neo4j 用 Docker Compose。API Key 通过环境变量注入。

## 5. 答辩注意事项

### 5.1 该强调的

- ✅ 「工具算数 + LLM 解读」的分层设计
- ✅ 三种 Agent 范式覆盖不同复杂度
- ✅ Pipeline vs Emergent 两种技能执行范式
- ✅ 三层记忆 + RRF 混合 RAG
- ✅ 事件驱动的可观测 Agent
- ✅ 完整的全栈交付（前后端 + 基础设施）

### 5.2 该诚实说明的

- ⚠️ LangGraph 在 README 中提及但代码未使用
- ⚠️ Provider 切换前端未完全打通 Chat
- ⚠️ 流式输出是模拟分块，非 LLM 原生 token 流
- ⚠️ 无 Docker 时记忆/RAG 功能降级
- ⚠️ 暂无自动化测试

**主动说明这些点反而体现你对项目的全面理解。**

### 5.3 演示技巧

1. **先简后繁** — 先 ReAct 简单 demo，再审计 Pipeline，最后辩论
2. **边演示边讲** — 不要沉默等结果，讲解当前阶段在做什么
3. **指给评委看** — 工具调用列表、事件类型、报告结构
4. **准备 backup** — 截图/录屏/API Key 失效时的备用方案
5. **控制时间** — 审计 + 辩论是核心，各 5 分钟，其余压缩

## 6. 一句话总结（答辩收尾）

> 本项目是一个面向会计学场景的全栈 LLM Agent 平台，核心创新在于：用确定性工具保证财务计算准确性，用三种 Agent 引擎（ReAct / Plan-Execute / Multi-Agent 辩论）覆盖不同复杂度的分析任务，用技能 Pipeline 固化审计 SOP，用三层记忆和混合 RAG 增强领域上下文。整体架构分层清晰、模块可插拔，具备向生产环境演进的基础。
