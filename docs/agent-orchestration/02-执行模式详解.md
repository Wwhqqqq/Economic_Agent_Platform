# 执行模式详解

> 本文说明聊天页首页四个选项——**智能路由 / 推理闭环 / 任务编排 / 协同决策**——分别是什么、底层用哪套 Agent 引擎、与 ReAct / Plan-Execute / Multi-Agent 等范式的对应关系，以及实际使用建议。

## 1. 核心结论

首页四个选项是 **执行模式（execution mode）** 的选择，不是 UI 样式或简单参数切换。它们决定 `AgentOrchestrator` 调度哪套 **Agent 编排引擎** 来处理用户输入。

| 首页选项 | 内部 key | 底层 Agent | 核心范式 |
|---------|----------|-----------|---------|
| **智能路由** | `adaptive` | 无（路由器） | 按关键词自动选择下面三种之一 |
| **推理闭环** | `reasoning_action` | `ReActAgent` | **ReAct**（推理 → 调工具 → 观察 → 再推理） |
| **任务编排** | `task_orchestration` | `PlanExecuteAgent` | **Plan-Execute**（先规划，每步内嵌 ReAct） |
| **协同决策** | `collaborative_decision` | `AccountingDebateTeam` | **Multi-Agent 辩论**（多角色，各角色内部 ReAct 式工具循环） |

**平台没有单独的 CoT（Chain of Thought）模式。** 链式思考会体现在流式输出的「思考中 / 推理文本」事件中，但架构上主打 **ReAct**，并在其上叠加 Plan-Execute 与 Multi-Agent。

Legacy 别名（兼容旧接口）：

| Legacy key | 规范 key |
|------------|----------|
| `auto` | `adaptive` |
| `react` | `reasoning_action` |
| `plan_execute` | `task_orchestration` |
| `multi_agent` | `collaborative_decision` |

---

## 2. 整体架构

用户在前端选择模式并发送消息后，请求经 WebSocket 进入 `AgentOrchestrator`，由编排器规范化模式、（可选）智能路由，再实例化对应 Agent 执行。

```
用户选择模式 + 输入问题
        │
        ▼
  AgentOrchestrator
        │
        ├─ adaptive（智能路由）──► 关键词扫描 ──► 选下面三种之一
        │
        ├─ reasoning_action ──► ReActAgent
        ├─ task_orchestration ──► PlanExecuteAgent
        └─ collaborative_decision ──► AccountingDebateTeam
                │
                ▼
        共享能力：SkillRegistry / ToolRegistry / MemoryManager / LLMFactory
                │
                ▼
        WebSocket 流式事件 → 前端 ChatView
```

**代码入口：**

- 编排器：`backend/app/agent/orchestrator.py`
- 模式元数据：`backend/app/core/catalog.py`
- WebSocket 传参：`backend/app/api/chat.py`（`mode` 字段）
- 前端模式选择：`frontend/src/views/ChatView.vue`、`frontend/src/stores/settings.ts`

## 3. 智能路由（adaptive）

### 3.1 是什么

智能路由 **不是第四种 Agent 算法**，而是编排器里的 **自动调度层**。用户选「智能路由」时，平台会根据问题文本中的关键词，在后三种引擎中自动选一个。

### 3.2 路由规则

实现位于 `orchestrator.py` 的 `_select_mode()`：

```python
complex_keywords = ["分析", "审计", "评估", "报告", "计划", "对比", "审核", "尽调"]
debate_keywords = ["辩论", "讨论", "评审", "多方", "角度", "委员会"]

if any(kw in user_input for kw in debate_keywords):
    return "collaborative_decision"
if any(kw in user_input for kw in complex_keywords):
    return "task_orchestration"
return "reasoning_action"
```

**优先级：** 辩论类关键词 > 复杂任务关键词 > 默认 ReAct。

### 3.3 适用场景

- 日常混用、不确定任务复杂度
- 希望「问一句就自动选对引擎」的默认体验

### 3.4 注意事项

- 路由仅基于 **关键词匹配**，不是语义理解模型；表述不含上述词时，复杂任务也可能被分到 ReAct。
- 若明确需要多步报告或多角色辩论，建议 **手动选择** 对应模式，避免误路由。

## 4. 推理闭环（reasoning_action）

### 4.1 是什么

对应 **`ReActAgent`**，实现经典的 **ReAct（Reasoning + Acting）** 循环：模型推理 → 决定是否调用工具 → 执行工具 → 将结果作为 Observation 写回上下文 → 继续推理，直到产出最终文本。

### 4.2 执行流程

1. **配置规范化**：session_id、provider、temperature、max_iterations 等。
2. **Prompt 组装**：激活技能（若有）的系统 Prompt + Agent 默认 Prompt + MemoryManager 注入的 RAG / 长期记忆 / 图谱 / 短期历史。
3. **工具绑定**：从 `ToolRegistry` 取 LangChain 工具；若技能激活，仅暴露技能声明的 `required_tools` 子集。
4. **ReAct 循环**（最多 `AGENT_MAX_ITERATIONS` 次，默认 10）：
   - `THINKING` 事件 → 调用 LLM（带 tools）
   - 若返回 `tool_calls`：执行工具，推送 `TOOL_CALL` / `TOOL_RESULT`，继续下一轮
   - 若返回纯文本：视为最终答案，推送 `REASONING` 流式片段 → `FINAL` → `DONE`
5. **记忆持久化**：可选写入会话记忆。

### 4.3 与 CoT 的区别

| 维度 | CoT（链式思考） | ReAct（本项目推理闭环） |
|------|----------------|------------------------|
| 核心 | 一步步推理，通常不强制调外部工具 | 推理与 **行动（工具调用）** 交替 |
| 信息来源 | 主要依赖模型内部知识 | 强调工具 Observation 驱动结论 |
| 在本项目 | 无独立模式 | 单 Agent 默认引擎 |

### 4.4 适用场景

- 普通问答、信息检索、计算验证
- 单次或少量工具调用
- 延迟要求较低、任务结构简单

### 4.5 代码位置

- `backend/app/agent/react_agent.py`
- `backend/app/agent/runtime.py` → `run_react_loop()`

## 5. 任务编排（task_orchestration）

### 5.1 是什么

对应 **`PlanExecuteAgent`**，采用 **Plan-Execute** 范式：先把复杂目标拆成 JSON 步骤计划，再逐步执行，最后评估、可选重规划、汇总报告。

**重要：Plan-Execute 不是 ReAct 的替代品，而是在 ReAct 外包一层规划器；每个子步骤内部仍跑 ReAct。**

### 5.2 五阶段流水线

```
用户任务
   │
   ▼
① Plan（规划）      ── LLM 输出 JSON：overview + steps[]
   │
   ▼
② Execute（逐步执行）── 每个 step 独立跑 ReAct（persist_memory=False）
   │
   ▼
③ Evaluate（评估）  ── LLM 判断结果是否充分
   │
   ▼
④ Replan（可选）    ── 最多 1 次，根据评估反馈重新规划并执行
   │
   ▼
⑤ Aggregate（汇总） ── ReAct 将所有步骤结果综合成最终报告，写入记忆
```

### 5.3 与 ReAct 的差异

| 维度 | 推理闭环（ReAct） | 任务编排（Plan-Execute） |
|------|------------------|-------------------------|
| 任务拆解 | 隐式，在 ReAct 循环中完成 | 显式 JSON 计划 + 步骤时间线 |
| 子步骤记忆 | 写入会话 | 子步骤不写记忆，避免污染 |
| 前端事件 | THINKING / TOOL_* / REASONING | 额外有 `STEP`、`INTERMEDIATE` |
| 温度策略 | 默认用户 temperature | 规划/评估阶段偏低（0.2–0.3） |

### 5.4 容错

若 LLM 返回的 plan 不是合法 JSON，会 fallback 为「单步执行整个任务」（退化为 ReAct）。

### 5.5 适用场景

- 财务审计、尽调、多章节分析报告
- 需要 **先拆任务、再逐步执行、最后合成** 的长任务

### 5.6 代码位置

- `backend/app/agent/plan_execute.py`

## 6. 协同决策（collaborative_decision）

### 6.1 是什么

对应 **`AccountingDebateTeam`（财务评审委员会）**，是 **Multi-Agent 辩论** 引擎：多个角色按轮次发言、质疑、裁决，每个角色内部通过 `run_prompt_tool_loop()` 做 ReAct 式工具调用。

### 6.2 三个固定角色

| 角色 | 定位 | 职责 |
|------|------|------|
| **财务分析师** | 正方 | 用工具做数据分析，提出有证据的结论 |
| **审计质疑官** | 反方 | 挑战假设，识别风险与会计红旗 |
| **投资裁决官** | 裁判 | 综合各方观点，给出最终裁决 |

### 6.3 执行流程（简化）

```
START
  │
  ▼
第 1 轮：分析师（带工具 ReAct）→ 质疑者（带工具 ReAct）→ 裁判总结
  │
  ▼
第 2 轮 …（最多 DEBATE_MAX_ROUNDS，默认 3）
  │
  ▼
最终裁决报告 → FINAL → DONE
```

### 6.4 与 ReAct / Plan-Execute 的关系

- **不是** 第四种单 Agent 算法
- **是** 多个 ReAct 角色 + 辩论协议 + 会计学领域 Prompt
- 每次请求 **新建** 辩论团队实例（ReAct / Plan-Execute 为常驻单例）

### 6.5 适用场景

- 财务评审、投资研判、合规风险评估
- 需要 **多角度碰撞、对抗式论证** 的演示或分析

### 6.6 前端快捷入口

聊天页「协同决策评审」快捷按钮会自动：

- 将模式设为 `collaborative_decision`
- 填入示例提示：「请对目标公司进行多视角协同决策分析」

### 6.7 代码位置

- `backend/app/multi_agent/accounting/debate_team.py`
- 详见 [多 Agent 模块](../multi-agent/README.md)

## 7. 范式对照总表

| 范式 | 是否有独立首页选项 | 在本项目中的落点 |
|------|-------------------|-----------------|
| **CoT（链式思考）** | ❌ | 流式 `REASONING` / `THINKING` 事件中可见推理过程，非独立架构 |
| **ReAct** | ✅ 推理闭环 | 单 Agent 核心引擎 |
| **Plan-Execute** | ✅ 任务编排 | 规划 + 分步 ReAct + 评估汇总 |
| **Multi-Agent** | ✅ 协同决策 | 三角色辩论，每角色内 ReAct |
| **智能路由** | ✅ 智能路由 | 元模式，自动选择上述三种 |

## 8. 与其他维度的关系（勿混淆）

执行模式与以下能力 **正交**，可组合使用：

| 维度 | 说明 | 影响范围 |
|------|------|---------|
| **技能（Skill）** | 如 `financial_audit` | 改 Prompt、限制工具集、记忆策略；任意模式可挂技能 |
| **工具（Tool）** | web_search、calculator、报表分析器等 | 在 ReAct 循环中被调用 |
| **记忆 / RAG** | MemoryManager | 所有模式共享上下文注入 |
| **LLM Provider** | DeepSeek / OpenAI / Anthropic 等 | 模型选择，不是执行模式 |
| **会话（Session）** | WebSocket session_id | 隔离对话历史 |

## 9. WebSocket 事件与前端表现

编排器与各 Agent 通过结构化事件驱动前端 UI：

| 事件类型 | 含义 | 典型前端表现 |
|----------|------|-------------|
| `START` | 任务开始 | 附带 execution_mode、active_skill |
| `THINKING` | 模型正在推理 | 「正在思考…」动画 |
| `TOOL_CALL` / `TOOL_RESULT` | 工具调用与结果 | 工具卡片 |
| `REASONING` | 流式文本片段 | Markdown 逐段渲染 |
| `CITATION` | 知识库引用 | 引用卡片 |
| `STEP` / `INTERMEDIATE` | 计划步骤 / 中间产物 | Plan-Execute 时间线 |
| `FINAL` | 最终答案定稿 | 完整内容与 token 统计 |
| `DONE` | 全流程结束 | 关闭 loading |

## 10. 使用建议

| 场景 | 推荐模式 |
|------|---------|
| 普通问答、算数、查资料 | **推理闭环** 或 **智能路由** |
| 「对某公司做完整财务审计并出报告」 | **任务编排**（或智能路由 + 「审计/报告」等关键词） |
| 「多角度评审是否值得投资」 | **协同决策** |
| 不确定用哪种 | **智能路由**（默认） |

**同一条问题的差异示例（「分析某公司 2024 年财报」）：**

| 模式 | 实际行为 |
|------|---------|
| 智能路由 | 含「分析」→ 自动走路由到 **任务编排** |
| 推理闭环 | 单轮或多轮 ReAct，可能调 1–2 个会计工具后直接给结论 |
| 任务编排 | 先出计划（读报表 → 算比率 → 现金流 → 写报告），逐步执行后汇总 |
| 协同决策 | 分析师给结论 → 质疑者挑漏洞 → 裁判裁决，多轮往复 |

## 11. 会员权限（规划 vs 现状）

多用户文档（`docs/多用户/04-权限与租户隔离/`）中的 **规划**：

| 能力 | 普通用户 | 会员 |
|------|---------|------|
| `reasoning_action` | ✓ | ✓ |
| `adaptive` → 仅路由到 ReAct | ✓ | ✓ |
| `task_orchestration` | ✗（403） | ✓ |
| `collaborative_decision` | ✗（403） | ✓ |
